# CareSeeker Web (`apps/web`)

Single **Vite + React + TypeScript** app that builds **four product variants** from the same codebase. UI uses **MUI**, **TanStack Query**, **React Router**, and **Supabase JS** for auth where needed.

## App variants (`VITE_APP_VARIANT`)

| Variant    | Intended host              | Role                                                         |
| ---------- | -------------------------- | ------------------------------------------------------------ |
| `core`     | careseeker.com (marketing) | Landing, about, basic login/register placeholders            |
| `client`   | client.careseeker.com      | Care seeker portal (dashboard + route placeholders)          |
| `provider` | provider.careseeker.com    | Care provider portal (dashboard + route placeholders)        |
| `admin`    | admin.careseeker.com       | **Internal admin app** — auth + route protection (see below) |

The variant is fixed at **build time** via `VITE_APP_VARIANT`. In development, each `start:*` script sets it for that server instance.

## Admin app (implemented)

Admin is **not** a separate codebase; it is the `admin` variant with dedicated modules under `src/services/admin/` and `src/routes/adminRoutes.tsx`.

- **Login:** `/login` — Supabase `signInWithPassword`, then **`GET /admin/me`** on the API. A valid Supabase session **alone** is not enough; non-admins are **signed out** and see: _“Your account is not authorized to access the admin panel.”_
- **Protection:** `RequireAdmin` route guard + `AdminAuthProvider` (only mounted when variant is `admin`). All admin pages except `/login` wait on a shared loading screen until session + `/admin/me` succeed; otherwise redirect to `/login`. No flash of protected chrome before validation.
- **Logout:** Admin layout includes **Log out** (sidebar on desktop, button above content on mobile) → `signOut` + navigate to `/login`.
- **Reusable module:** `src/services/admin/auth/` — barrel `index.ts` exports `AdminAuthProvider`, `useAdminAuth`, `RequireAdmin`, `fetchAdminMe`, `AdminAuthLoadingScreen`, etc. **`GET /admin/me`** integration lives in `adminMe.ts`.
- **Routes:** `/dashboard` (default), `/careseekers`, `/care-providers`, `/open-jobs`, `/payments-history`, `/reports`; `/` redirects to `/dashboard`; aliases `/jobs` → `/open-jobs`, `/payments` → `/payments-history`.

Client and provider variants do **not** load admin auth — isolation is enforced by `main.tsx` (provider wraps `App` only for `admin`).

## Core / client / provider

- **Routing:** `src/routes/coreRoutes.tsx`, `clientRoutes.tsx`, `providerRoutes.tsx`, `adminRoutes.tsx`; `App.tsx` picks the router from `getAppVariant()` in `src/config/appVariant.ts`.
- **UI:** Feature folders under `src/services/<variant>/` (e.g. `services/core/pages`, `services/admin/…`).
- **Client registration:** `services/client/pages/Register/` starts with "Who needs care?" (`steps/CareForStep.tsx`). _For myself_ continues with the existing create-account → about-you → care & health steps. _Family member or friend_ opens the **on-behalf** multi-step flow (`ON_BEHALF_REGISTER_STEPS` in `types.ts`, progress in `components/OnBehalfRegisterStepper.tsx`): step 1 (`steps/RegistrantInfoStep.tsx`) collects the registrant — the person opening the account (name, email, US phone, relationship to the care recipient, password, consent) — and creates the account via `POST /seeker/register/on-behalf`, then signs in; step 2 (`steps/RecipientPersonalInfoStep.tsx`) describes the person who needs care (name, date of birth, gender, US address, living situation, mobility, languages, ethnicity, a few words about them) and is saved with `PUT /seeker/care-recipient`; step 3 (`steps/CareNeedsStep.tsx`, form model + catalogues + mappers in `carePreferencesForm.ts`) starts with “one-time visit or ongoing care?” and adapts: a **one-time visit** asks what it is about (tasks + optional notes), the date and hours, and a required budget; **recurring care** asks the tasks, weekly hours / duration / start, the weekly schedule (the provider's `WeeklyScheduleField` limited to “All day” / “Specific hours”), live-in and emergency needs, with an optional budget. Both then ask special requirements (pets, home accessibility, care instructions) and caregiver preferences (gender, language, qualifications, experience, cultural considerations). The budget is hourly or a fixed price (for the visit / per visit). Tasks use the provider vocabulary (`utils/careOptions.ts`) and are the only “what help is needed” question of the flow; answers they imply are not asked again (driving → car, with a wheelchair-accessible follow-up; pet care → pets; overnight hours → overnight care). Saved with `PUT /seeker/care-preferences`; until saved or edited it starts from suggestions derived from step 2 (`suggestCarePreferences`: mobility → mobility task / accessible car, first language → caregiver language), flagged to the user. Saving step 3 calls `POST /seeker/onboarding/complete` and opens the **one-time review page** (`/register/review`, `pages/Review/ClientRegistrationReview.tsx`, fed by `GET /seeker/onboarding`): a standalone page (no app chrome), mirroring the provider overview, where every section (registrant, care recipient, care needs) can be edited in place (`components/profile-editors/`, which reuse the step forms) and where two buttons finish: **Confirm and go to dashboard** (`POST /seeker/onboarding/confirm`) or **Confirm and open a job now** (confirms, then opens the new-job page below; the note under the buttons explains that registration alone does not post a job and that a job post will be prefilled from these answers). `auth/RequireSeekerOnboarding.tsx` gates the app for on-behalf accounts like the provider's `RequireOnboarding`: unfinished → `/register`, finished-but-unconfirmed → `/register/review`, confirmed → `/register/review` redirects to the dashboard; self-registered accounts always pass. Back / continue move freely between the steps: once the account exists, step 1 switches to `mode="edit"` (email read-only, no password / consent) and saves with `PUT /seeker/registrant`. A signed-in seeker opening `/register` with an unfinished on-behalf registration resumes at the first unfinished step with everything prefilled (`GET /seeker/registrant`, `/seeker/care-recipient`, `/seeker/care-preferences`); others are sent to the dashboard. Client-side rules live in `validation.ts` and mirror the API.
- **New job post:** `/jobs/new` (`services/client/pages/NewJob/`) has two entry points, told apart by `?mode=` (`jobStartMode.ts`; kept in the URL so a reload keeps the choice and Back returns to it). **After registration**, "Confirm and open a job now" opens `?mode=prefill` directly. **"Add New Job"** opens `/jobs/new`, which first asks how to start (`JobStartChooser.tsx`): _Prefill with account info_ (`?mode=prefill`; unavailable, with the reason, when the account has no saved care needs — e.g. registered for oneself) or _Create a new post_ (`?mode=blank`, an empty form). Both use the same editor (`JobPostEditor.tsx`, form model + validation in `jobPostForm.ts`). Prefill loads `GET /seeker/jobs/draft`: the care recipient's city / state / ZIP (never the street address), the saved care needs and a generated title and short description. Everything stays editable: title, description, location and the care details, which are the same questions as registration step 3 (`components/CareNeedsFields.tsx`, shared with `CareNeedsStep`, same form model and rules). "Write / Rewrite from the details" asks `POST /seeker/jobs/draft/text` for a title and description from the current details (with Undo). Editing a job never changes the profile. Nothing is saved until **Submit job** (`POST /seeker/jobs`); **Cancel** asks for confirmation ("everything you entered for this job post will be deleted", registration details are not affected), as does leaving with unsaved changes — including "Start differently" / Back to the choice (in-app navigation is blocked with the same dialog, closing the tab gets the browser prompt). A prefilled one-time visit whose date has passed is flagged. After posting, the page offers the dashboard or another job post (back to the choice).
- **Open jobs overview:** `/jobs` (`services/client/pages/OpenJobs/`) lists the seeker's jobs that are still running as MUI cards (`JobOverviewCard.tsx`): status chip, title (links to the job), schedule / place / budget, short description, then either the hiring funnel — AI-recommended caregivers, applicants (with "+N new"), interviewing — or, once **hired**, the caregiver (rating, next visit) and a billing panel (`JobBillingPanel.tsx`: billable hours this week, "no hours yet", invoice due / overdue, fixed price to pay, or "All is good" when paid). Statuses (`JobPostStatus` in `queries/client/openJobsOverview.ts`, labels / colors / attention hints in `jobOverviewDisplay.ts`): `open`, `interviewing`, `offer_sent`, `hired`, `paused`; `completed` / `cancelled` / `closed` jobs are finished and never listed. The summary tiles (active jobs, new applicants, interviewing, payments due) and the status chips both filter the cards (`jobsFilter.ts`, kept in the URL as `?show=` / `?status=` so Back from a job page restores the view; clicking the active tile clears it). Also: loading skeletons and an empty state (`/jobs?preview=empty`).
  - **Job links:** every job is addressed by its public **`jobId`** (same format as the API's `jobs.jobId`), e.g. `/jobs/3f9a1c2b7d4e8f60` (`jobLinks.ts`). The card buttons (Review applicants, See recommendations, View candidates, View offer, View timesheet, View job, Resume job, Messages), the title and "View job post" open the job page, with `?section=` naming the part they are about (the page scrolls there and highlights it); the list view (filters included) is remembered for "← Open jobs". **Pay now** is not built yet (a notice).
  - **Job page (seeker view):** `/jobs/:jobId` (`pages/Job/JobPage.tsx`, sections in `pages/Job/sections/`). Top: back link, **Copy job link**, **Pause / Resume** and **Close / Request to close** (`JobActionsBar.tsx`; disabled actions explain why). Top left: the job — status, posted, views, title, schedule / place / budget, description, tasks, job ID — with **Quick edit** (title + description, `JobDialogs.tsx`) for open jobs, a "Locked" chip with the reason otherwise. Right: **Messages**, **AI picked caregivers** (match score + reasons, invite to apply; "Backup caregivers" once hired) and **Interviewing**, then **Activity**. Below, by state — looking for a caregiver: **hiring progress** with the next step, the **offer** waiting for an answer, **applicants** (tabs by stage, proposed rate, match, cover note, shortlist / invite to interview); hired: **contract**, **payments** (the billing panel + invoices, Pay now) and **timesheet** — then the full **job requirements** (the registration review card, Edit → `/jobs/:jobId/edit`, which returns to the job page). Banners for paused jobs, pending closure requests and finished jobs (read-only). On phones: job → messages / candidates → details → activity. Candidates, conversations, activity, visits and invoices are sample data derived from each job (`queries/client/jobDetailsMock.ts`), consistent with its card; messaging, invitations, interviews, offers and payments show a notice.
  - **Rules** (`queries/client/jobPolicies.ts`, used by the UI and the mock service alike): only **open** jobs can be **edited** and **paused** (hidden from caregivers; resuming makes them open again — card menu and job page) — the menu explains why otherwise, and `/jobs/:jobId/edit` (`pages/Job/EditJobPage.tsx`, the job post form in its edit variant) refuses with the reason. **Closing** an open job happens right away after a confirmation and moves it to the archive (`closed`). Any other running job needs a **request** with a reason and an explanation for an admin to approve (`CloseJobDialog.tsx`); in the interview phase (interviewing / offer sent) or once hired the seeker is warned that a payment compensation may be asked and must acknowledge it. A pending request shows on the card and disables closing. Admin approval itself is not built yet.
  - **Data — real jobs or the demo:** every job screen (new job, open jobs, job page, edit, quick edit, pause / resume, close) goes through `queries/client/jobsService.ts`, which has two implementations. **Signed in**, it is the API (`jobsApi.ts`: `GET /seeker/jobs[/:jobId]`, `PUT /seeker/jobs/:jobId`, `POST …/pause | resume | close`, plus the draft / text / create endpoints); the backend enforces the same rules (`apps/api/src/seeker/jobs/job-policies.ts`). Hiring does not exist on the backend yet, so a real job's AI matches, applicants, interviews, messages and payments are empty, views are not shown, its activity comes from its dates (posted, edited, paused, closed), and closing a paused job (which needs an admin) explains that and offers to resume it first. **In a demo session** it is the sample data (`openJobsOverview.ts`, `jobDetailsMock.ts`), kept in `localStorage` (job links work across tabs and reloads; re-seeded daily with the same job ids), where jobs posted in the demo are added too.
- **Demo login ("Explore with sample data"):** the client login page offers a demo next to the normal sign-in, for presentations. It signs in to a session that lives only in the browser (`queries/client/demoMode.ts`; `ClientAuthContext` treats it as a signed-in seeker without asking the API) and opens the open jobs page with the sample data. Everything works without an account or a reachable backend — the demo makes no API requests: the account is a registered, confirmed seeker (`demoProfile.ts`: Sarah Carter, who registered for her father Walter), new job drafts are prefilled from it, and titles / descriptions are written by a compact client-side version of the API's templates. A banner shows the demo with **Exit demo**; starting and ending a demo clears the query cache, so sample and real data never mix.
- **Shared form building blocks** (used by provider onboarding and the client registration): `components/FormLayout.tsx` (`FormSection`, `FieldRow`, `SwitchRow`), `components/DateOfBirthField.tsx`, `components/UsAddressFields.tsx`, `components/CheckboxGroupField.tsx`, `components/DescribedRadioGroup.tsx`, `components/WeeklyScheduleField.tsx` (day modes, legend and labels passed by each flow), `components/PasswordTextField.tsx`; `utils/` holds the matching rules and catalogues (`careOptions.ts`, `weeklySchedule.ts`, `money.ts`, `dateOfBirth.ts`, `usAddress.ts`, `usStates.ts`, `usPhone.ts`, `gender.ts`, `focusField.ts`).
- **Provider registration:** `services/provider/pages/Register/` is a multi-step onboarding flow (`types.ts` → `ProviderRegisterStep` / `PROVIDER_REGISTER_STEPS`, one component per step under `steps/`, shared inputs under `components/`). Steps 1 (personal information + profile picture) and 2 (services & job interests, option catalogues in `serviceOptions.ts`) are filled in locally with back / continue; submitting step 2 posts step 1 to `POST /provider/register`, signs in, verifies `GET /provider/me` and saves step 2 with `PUT /provider/service-profile`. Step 3 (documents, `documentOptions.ts`, drag & drop via `components/DocumentDropzone.tsx`) uploads each file immediately through `/provider/documents` with per-file progress, replace and remove; files are fetched back through the authenticated download endpoint, so the UI is independent of the storage backend. Step 4 (availability & work preferences, `workPreferenceOptions.ts`, weekly schedule in `components/WeeklyScheduleField.tsx` with MUI time pickers) is saved with `PUT /provider/work-preferences` on "Finish", which then calls `POST /provider/onboarding/complete` and opens the **one-time review page** (`/overview`, `pages/Overview/`, fed by `GET /provider/overview`): a standalone page (no app chrome) where every section can be edited in place (`components/profile-editors/`) and "Confirm" (`POST /provider/onboarding/confirm`) opens the dashboard. `auth/RequireOnboarding.tsx` guards every provider route: unfinished onboarding → `/register`, finished-but-unconfirmed → `/overview` (refreshing or leaving brings the provider back there until confirmation succeeds), and after confirmation `/overview` itself redirects to the dashboard. A failed status check shows an error with Retry / Sign out — it never falls back to the app. After onboarding, everything is edited in **Account settings** (`pages/AccountSettings/`, `?tab=personal|services|documents|availability|account`), which reuses the onboarding step forms per section (step 1 in `mode="edit"`); the `/profile/*` and `/availability` pages show the same data read-only with Edit links into the matching tab. `/register` asks `GET /provider/onboarding` for signed-in providers: unfinished ones resume at the first open step (steps 2 and 4 prefilled from the server, step 3 with their uploaded documents), and completed providers are redirected to the dashboard. Client-side rules live in `validation.ts` and mirror the API.

## Environment (`apps/web`)

Vite only exposes variables prefixed with **`VITE_`**. For **Vercel (staging)** and production frontends, configure at least:

| Variable                                | Purpose                                                                                                                                                     |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VITE_PUBLIC_BASE_URL`                  | Public URL of **this** deployment (e.g. `https://admin-careseeker.vercel.app`). Used for auth redirect base / public URL resolution in `env.publicBaseUrl`. |
| `VITE_APP_VARIANT`                      | Which app is built: `core` \| `client` \| `provider` \| `admin`. **Required in production** (see `src/config/appVariant.ts`).                               |
| `VITE_SUPABASE_URL`                     | Supabase project URL (needed wherever Supabase Auth runs, e.g. admin login).                                                                                |
| `VITE_SUPABASE_PUBLISHABLE_DEFAULT_KEY` | Supabase **anon** / publishable key (browser-safe).                                                                                                         |

Optional (defaults apply if unset):

| Variable                              | Purpose                                                                                                                                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `VITE_API_BASE_URL` or `VITE_API_URL` | Backend API origin. If unset: `http://localhost:2000` on localhost, else `https://backend.careseeker.app`.                                                                                                                                 |
| `VITE_AUTH_MODE`                      | `supabase` or `local`. Defaults to `local` when the Supabase variables are missing, so the apps run in a closed environment against an API started with `AUTH_MODE=local` (see `apps/api/README.md`). Sessions are kept in `localStorage`. |

**Admin “back to home”** uses `env.mainPlatformUrl` (hostname-based: local / `*.localhost` → `http://localhost:3000`, otherwise `https://careseeker.app`), not `VITE_PUBLIC_BASE_URL`.

Use `.env` / `.env.local` / Vercel project env (gitignored locally); do not commit secrets.

## Scripts

From `apps/web`:

```bash
pnpm run start:core      # VITE_APP_VARIANT=core, port 3000
pnpm run start:admin     # admin variant, port 3001
pnpm run start:provider  # port 3002
pnpm run start:client    # port 3003
pnpm run start:all       # all four (see concurrently output)
pnpm run build:core      # … build:client, build:provider, build:admin
pnpm run lint
```

From monorepo root: `pnpm start:core`, `pnpm start:admin`, etc., or `pnpm start:all`.

## Dev proxy (optional)

`scripts/dev-proxy.js` — single entry port (e.g. 3000) routing `admin.localhost`, `client.localhost`, etc. to the per-variant Vite ports. Read the script header for the intended port map (may differ slightly from `start:*` default ports).
